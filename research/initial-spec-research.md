# CalDAV VTODO for a Task Backend: A Technical Capability and Limitations Assessment

## TL;DR
- CalDAV/VTODO is a viable **sync substrate** but not a complete task-application backend: the iCalendar data model (RFC 5545 §3.6.2) covers core fields (priority, status, due, categories, subtasks via RELATED-TO) but the real ceiling is **client divergence**, not the spec. Build a hybrid: CalDAV for interop, your own API/store for advanced features.
- The single most important architectural fact: **clients are wildly inconsistent**. Apple Reminders and Tasks.org honor subtasks (RELATED-TO;RELTYPE=PARENT) and X-APPLE-SORT-ORDER; Thunderbird and GNOME Evolution flatten hierarchies; Google's CalDAV API "Doesn't support VTODO or VJOURNAL data" at all. There is no "write once, sync everywhere" guarantee for anything beyond a minimal VTODO.
- With **zero proprietary extensions** you reliably get: title, notes, due/start dates, priority, status, percent-complete, categories/tags, and parent/child subtasks. Everything else (manual sort order, kanban columns, per-user completion, dependencies, time tracking, rich text) requires X- properties or a side channel that most clients silently ignore or strip from their UI.

## Key Findings

1. **The protocol ceiling is generous; the client ceiling is low.** RFC 5545 defines a rich VTODO grammar, and RFC 9253 ("Support for iCalendar Relationships," M. Douglass, published 1 August 2022, DOI:10.17487/RFC9253) adds project-management relationships (DEPENDS-ON; the temporal types FINISHTOSTART/FINISHTOFINISH/STARTTOFINISH/STARTTOSTART with a GAP parameter; FIRST/NEXT ordering; and the LINK, CONCEPT, and REFID properties) that, per its text, "allow the RELATED-TO property to define a richer set of relationships useful for project management." But almost none of RFC 9253 is implemented in mainstream task clients, and even RFC 5545 basics like RRULE-on-VTODO are handled inconsistently.
2. **Apple Reminders is the de facto reference for VTODO interop**, but only over classic iCloud CalDAV — and Apple moved its first-party Reminders to a proprietary non-CalDAV silo in iOS 13/macOS 10.15 (2019). Third-party CalDAV task sync against iCloud still works for non-upgraded lists.
3. **Tasks.org (Android) + DAVx5 is the best open-source "it just works" stack**, with nested subtasks of unlimited depth, recurrence, categories, and X-APPLE-SORT-ORDER-compatible manual ordering.
4. **Subtasks are the litmus test.** They work via RELATED-TO;RELTYPE=PARENT across Apple Reminders, Tasks.org, Nextcloud Tasks, jtx Board, and are stored by Baikal/SabreDAV — but Thunderbird and Evolution flatten them.
5. **Google Calendar's CalDAV rejects VTODO outright** — confirmed verbatim by Google's official CalDAV API Developer's Guide: "Doesn't support VTODO or VJOURNAL data." This is a hard constraint if Google interop matters.
6. **JSCalendar (RFC 8984) / JMAP is the strategic alternative**: a cleaner JSON task model (JSTask) that maps to VTODO, championed by Fastmail. But the JMAP Calendars specification explicitly states: "Unlike CalDAV, this specification does not define access to tasks or journal entries (VTODO or VJOURNAL iCalendar components in CalDAV)." So it is not a drop-in replacement today.

## Details

### 1. Protocol ceiling — what VTODO actually supports

**VTODO property inventory (RFC 5545 §3.6.2).** The ABNF allows, at most once: CLASS, COMPLETED, CREATED, DESCRIPTION, DTSTART, GEO, LAST-MODIFIED, LOCATION, ORGANIZER, PERCENT-COMPLETE, PRIORITY, RECURRENCE-ID, SEQUENCE, STATUS, SUMMARY, URL; at most once and mutually exclusive: DUE *or* DURATION (DURATION requires DTSTART); SHOULD-once: RRULE; and zero-or-more: ATTACH, ATTENDEE, CATEGORIES, COMMENT, CONTACT, EXDATE, RSTATUS, RELATED-TO, RESOURCES, RDATE, plus X-prop and IANA-prop. UID and DTSTAMP are REQUIRED.

Property semantics that matter for tasks:
- **STATUS** for VTODO is restricted to NEEDS-ACTION (default), COMPLETED, IN-PROCESS, CANCELLED. (Compare VEVENT's CONFIRMED/TENTATIVE/CANCELLED.)
- **PERCENT-COMPLETE** is an integer 0–100, valid only in VTODO. RFC 5545 §3.8.1.8: "A value of '0' indicates the to-do has not yet been started. A value of '100' indicates that the to-do has been completed."
- **PRIORITY** is 0–9 where 0=undefined, 1=highest, 9=lowest. Apple maps these to its three-level Low/Medium/High UI; many clients collapse the granularity.
- **DUE vs DTSTART/DURATION**: a VTODO with neither DTSTART nor DUE "specifies a to-do that will be associated with each successive calendar date, until it is completed" (RFC 5545 §3.6.2). DUE and DURATION must not co-occur.
- **CLASS** (PUBLIC/PRIVATE/CONFIDENTIAL), **GEO**, **CATEGORIES**, **SEQUENCE** (change counter), and **COMPLETED** (UTC date-time of completion) are all defined and widely stored, though UI exposure varies.

**Recurrence on tasks (RRULE).** This is the weakest core area. The RFC permits RRULE on VTODO, but the semantics of "what does a recurring task mean when completed" are underspecified, and implementations diverge badly. The Python `caldav` library (v3.2.1 docs) documents this directly: its `Todo.complete()` method notes "The RFC leaves a lot of room for interpretation on how to handle recurring tasks, and what works on one server may break at another." Two incompatible models exist in the wild:
   - **Tasks.org model**: on completion, mutate the single VTODO, advancing DTSTART/DUE to the next occurrence (so the completed instance disappears).
   - **Thunderbird/eM Client model**: on completion, create a *second* VTODO with the same UID for the completed instance, leaving the recurring master. This "two VTODOs with same UID" pattern confuses Tasks.org (documented in tasks/tasks issue #1600) and breaks todoman, which goes read-only when it sees multiple VTODO stanzas in one .ics (pimutils/todoman issue #304). Some servers schedule recurrences server-side; Tasks.org has an explicit "Let server schedule recurring tasks" toggle for servers such as mailbox.org. (Note: mailbox.org's CalDAV is restrictive in other ways too — it "does not allow creating task lists via CalDAV (it rejects MKCALENDAR)," per the google-tasks-to-caldav project.)

**Task hierarchies / subtasks (RELATED-TO;RELTYPE=PARENT/CHILD/SIBLING).** This is real and usable, not a paper feature — but only on clients that implement it. RFC 5545 §3.8.4.5/§3.2.15 define PARENT (default), CHILD, SIBLING. The dominant convention (Nextcloud Tasks, Apple Reminders, Tasks.org, jtx Board) is a child VTODO carrying `RELATED-TO;RELTYPE=PARENT:<parent-UID>` (or bare RELATED-TO, since PARENT is default). Baikal/SabreDAV store and pass through the property faithfully (a community report confirms "Subtasks are supported by Baikal. The resulting calendar files contain a RELATED-TO;RELTYPE=PARENT:[task identifier] field... It seems Thunderbird simply doesn't use this field."). **RFC 9253** (2022, updates 5545) substantially extends this with DEPENDS-ON, the temporal types FINISHTOSTART/FINISHTOFINISH/STARTTOFINISH/STARTTOSTART plus a GAP parameter for lead/lag, FIRST/NEXT ordering, REFID grouping, and a LINK property — explicitly "useful for project management." Adoption in task clients is essentially nil today; treat RFC 9253 as forward-looking.

**Attachments (ATTACH).** RFC 5545 allows ATTACH as either a URI reference or inline BASE64 binary, and it's legal on VTODO. Inline base64 is technically supported but operationally poor: RFC 8607 (CalDAV Managed Attachments, June 2019) notes "Use of inline attachment data is not ideal with CalDAV because the data would need to be uploaded to the server each time a change to the calendar data is made, even minor changes such as a change to the summary." Client support for task attachments is thin — Nextcloud's Deck/Tasks discussions explicitly list attachments as "not supported by Tasks yet."

**Alarms (VALARM in VTODO).** RFC 5545 permits VALARM sub-components inside VTODO; DAVx5/Tasks.org and the ZeppOS "Tasks NC" client use VALARM for task reminders. Support is more uneven than for VEVENT.

**Custom/extended properties (X-).** This is the crux for a server implementor. RFC 5545 explicitly allows X-prop on VTODO, and the survival convention is well-established. SabreDAV's client guide is explicit: "Clients may add non-standard properties to iCalendar objects. It is important that when you GET and later on PUT an updated iCalendar object, any non-standard properties you may not have built-in support for gets retained." Well-behaved clients (DAVx5, Tasks.org, Apple) preserve unknown X- properties on round-trip. **But "preserve on round-trip" is not "expose in UI" and not guaranteed across all clients** — a poorly written client can drop them, and you cannot rely on X- fields for server-authoritative logic if untrusted clients touch the object.

### 2. Extensions and augmentation protocols

- **CalDAV Scheduling (RFC 6638).** The machinery (ATTENDEE, ORGANIZER, scheduling Inbox/Outbox, SCHEDULE-AGENT, SCHEDULE-STATUS) is component-agnostic and *can* apply to VTODO — ORGANIZER and ATTENDEE are both legal VTODO properties, and PARTSTAT values include task-specific NEEDS-ACTION/ACCEPTED/DECLINED/IN-PROCESS/COMPLETED/DELEGATED. In practice, task assignment/delegation over iTIP is barely implemented; Nextcloud Deck's CalDAV integration discussion treats "assigned users → ATTENDEE or custom implementation" as an open design question, not a solved one. SCHEDULE-AGENT=SERVER vs CLIENT controls whether the server auto-delivers scheduling messages. Xandikos implements RFC 6638 end-to-end when all attendees are principals on the same server.
- **Managed Attachments (RFC 8607, not 8144).** Note the original query mislabels this as RFC 8144 — RFC 8144 is "Use of the Prefer Header Field in WebDAV"; the managed-attachments spec is **RFC 8607**. It lets a client POST an attachment that the server stores separately and references with `ATTACH;MANAGED-ID=...;FMTTYPE=...`. It explicitly covers "events or tasks." It is Informational (not Standards Track) "due to its noncompliance with multiple best current practices of HTTP" (everything is POST with query-param actions). iCloud and a few others deploy it; Nextcloud does not fully (open issue #5001).
- **CardDAV integration.** No standard links a VTODO to a CardDAV vCard. RFC 9253's LINK property (URI + REL) is the closest standardized path to "link a task to a contact," but it's unimplemented in task clients.
- **WebDAV Push (draft-bitfire-webdav-push / "WebDAV-Push").** This is the real-time story. It uses Web Push (RFC 8030) + VAPID (RFC 8292) + aes128gcm encryption (RFC 8291), built on UnifiedPush. **DAVx5 supports it from version 4.4.10 (still "experimental and subject of continuous improvement," per the DAVx⁵ manual).** Server side: a Nextcloud extension (`nc_ext_dav_push` / "DAV Push" app), the **Xandikos** server (`--webdav-push`), and the RustiCal server implement it. Thunderbird does **not** yet (open Mozilla Connect request). It works for any collection type including VTODO task lists. Without it, clients poll via CTag/sync-token.
- **JSCalendar (RFC 8984) / JMAP.** JSCalendar defines **JSTask**, which "maps to the iCalendar VTODO component type." It is cleaner than VTODO: native IANA time zones, PatchObject diffs, unambiguous recurrence, and a per-task `progress`/`status` model. RFC 8984 even solves per-instance recurring-task completion via recurrenceOverrides or splitting. **However, JMAP Calendars (jmap.io/spec-calendars) explicitly excludes tasks**: "Unlike CalDAV, this specification does not define access to tasks or journal entries (VTODO or VJOURNAL iCalendar components in CalDAV)." JSCalendar 2.0 (draft-ietf-calext-jscalendarbis, obsoletes 8984) is in progress (Feb 2026 draft). Fastmail authored both and uses JSCalendar internally. A practical bridge pattern exists: the Mailtemi client uses JSCalendar as its internal model with CalDAV and JMAP adapters at the edges. **Verdict: JMAP-for-tasks is not yet a shipping option; CalDAV/VTODO remains the only broadly interoperable task protocol in 2026.**
- **Proprietary server/client extensions.** Apple uses `X-APPLE-SORT-ORDER` for manual ordering (and other X-APPLE-* fields). Nextcloud uses CATEGORIES for tags (with a desire to integrate its native tagging). These are de-facto standards that some clients expect.

### 3. Client support landscape (what actually SYNCs, not just displays)

- **Apple Reminders (iOS/macOS) — gold standard, with a huge caveat.** Over classic iCloud CalDAV it syncs subtasks (RELATED-TO), priorities, due dates, notes, and uses `X-APPLE-SORT-ORDER` for manual order. BUT in iOS 13/macOS 10.15 (2019) Apple introduced "upgraded reminders" that migrate first-party Reminders into a **proprietary CloudKit silo not accessible via CalDAV**. BusyCal and Tasks.org both document this: upgraded Reminders "uses a proprietary format that is not compatible" and data "will no longer appear in BusyCal or other third-party apps." Third-party CalDAV clients hitting iCloud's CalDAV endpoint still work for non-upgraded task lists. Apple Reminders subtasks: completing/deleting/moving a parent cascades to children.
- **Tasks.org (Android) — best open-source CalDAV task client.** Nested subtasks of unlimited depth, powerful recurrence, categories/tags, EteSync/CalDAV/Google sync, shared lists (Nextcloud/ownCloud/SabreDAV/OX). Manual order via `x-apple-sort-order`, documented as "compatible with Apple Reminders and Nextcloud Tasks." Shared lists are explicitly **not** available over plain DAVx5 sync ("due to technical limitations").
- **OmniFocus** — does not sync tasks via CalDAV; uses its own Omni Sync Server (WebDAV-based for its proprietary database), not VTODO interop.
- **Fantastical / BusyCal (macOS)** — read/write Apple Reminders' local store rather than implementing independent VTODO sync engines; BusyCal "reads directly from Apple's Reminders database... It does not have its own sync engine for tasks."
- **GNOME Evolution** — supports CalDAV VTODO but **flattens subtask hierarchy** (does not use RELATED-TO).
- **Thunderbird** — supports VTODO tasks but, per a 21-year-old open bug (Mozilla bug #194863), does **not** implement subtasks/RELATED-TO and flattens hierarchy; its recurring-task completion model (duplicate VTODO with same UID) conflicts with Tasks.org. Recurring tasks have long-standing bugs (bug #373775 — "Marking repeated task complete marks all instances"). WebDAV-Push is not supported.
- **CLI/developer clients:**
  - **DAVx5** — the Android sync adapter; syncs "Tasks (VTODO via CalDAV)" and routes them to a tasks app (Tasks.org, jtx Board, OpenTasks). Uses CALDAV:supported-calendar-component-set to classify collections. Does WebDAV-Push (≥4.4.10).
  - **vdirsyncer** — storage-agnostic; `item_types = ["VTODO"]`, treats each task as one opaque .ics, preserving all properties including X-. Cannot sync VTODO to Google (server rejects it).
  - **todoman** — supports SUMMARY, DESCRIPTION, LOCATION, DUE, PRIORITY (degraded to none/1 only), STATUS (complete only); PERCENT-COMPLETE is 0/100 only. **No recurrence (RRULE) and no subtasks (RELATED-TO)** — open issues #304 and #396. Unsupported fields are preserved on disk, "never deleted or altered."
  - **khal** — **no VTODO support at all** (events only); tasks delegated to todoman in the pimutils ecosystem (open issues #10, #448).

### 4. The edgy features

- **Kanban board in pure CalDAV.** Achievable with no server extensions using the Nextcloud Deck mapping: Board→VCALENDAR (collection), List/Stack→a root VTODO with no RELATED-TO, Card→VTODO with RELATED-TO to its stack, subtask→further nesting, tags→CATEGORIES (per nextcloud/deck issue #15/#2399). Nextcloud's own Deck team prototyped exactly this. The limitation: columns/stacks-as-tasks is a convention only your app and cooperating clients understand; generic clients see a flat or nested task list, not a board. Nextcloud also notes that tags, assigned users, attachments, and recurrence may need to fall back to non-CalDAV storage.
- **Manual sort order.** No standard property exists. The de-facto solution is `X-APPLE-SORT-ORDER` (integer), honored by Apple Reminders, Tasks.org, Nextcloud Tasks, and elementary Tasks (which added it explicitly because "the VTODO RFC does not support a 'standard' way of sorting"). Without it you fall back to PRIORITY or DUE-based sorting. (Note: Apple Reminders itself historically treats sort as a *view* setting, syncing manual order via X-APPLE-SORT-ORDER but not other sort modes across all clients.)
- **Collaborative per-user completion state.** Not representable in CalDAV's data model. A VTODO is a single shared object; STATUS/PERCENT-COMPLETE/COMPLETED are single-valued for the whole component. RFC 5545's PERCENT-COMPLETE-per-assignee language assumes iTIP REPLY aggregation, which no task client implements. "One user completes, others still see incomplete" requires either per-user copies (a UID-management nightmare) or a custom API. This is a hard architectural limit.
- **Rich text / Markdown in DESCRIPTION.** DESCRIPTION is plain text (RFC 5545 TEXT value). The widely-used HTML alternative is the non-standard `X-ALT-DESC;FMTTYPE=text/html` (Microsoft origin). Apple Calendar/Reminders generally ignore X-ALT-DESC; support is patchy. Most task clients preserve but don't render Markdown — it round-trips as literal text.
- **Dependencies (blocking/blocked-by).** RFC 9253's DEPENDS-ON and FINISHTOSTART exist but are unimplemented in task clients. No widely-adopted support.
- **Time tracking / logged hours.** No standard or convention in iCalendar. (The abandoned "Task Extensions to iCalendar" draft defined ESTIMATED-DURATION, but not actuals.) Requires X- properties or a side channel.

### 5. Interoperability traps

- **Escaping.** TEXT values must escape backslash (`\\`), semicolon (`\;`), comma (`\,`), and newline (`\n`/`\N`); colon is NOT escaped. Commas are list separators for CATEGORIES and multi-valued properties. Failing to escape commas is the single most common bug and breaks strict parsers (e.g., Google's importer). Historically clients have had decode bugs (Mozilla bug #307948: escaped chars not unescaped in DESCRIPTION/LOCATION). The icalendar library has shipped fixes for round-trip CATEGORIES corruption when category values contain commas.
- **Line folding.** Lines SHOULD be ≤75 octets, folded by CRLF + single leading space/tab; unfold before parsing. Folds must not occur mid-tag (Mozilla bug #273039 generated illegal folds before the `:`), and must not split a UTF-8 multibyte sequence. Base64 ATTACH makes folding performance-sensitive (the icalendar library cut a 1 MB fold from minutes to milliseconds).
- **Silent property stripping.** Clients that don't implement round-trip preservation will drop X- properties and unknown fields — so never put server-authoritative state solely in fields a client might strip. RELATED-TO is dropped/ignored by Thunderbird and Evolution (flattening subtasks).
- **UID/SEQUENCE/ETag.** UID must be unique within the collection. SEQUENCE is a change counter. ETag (getetag) drives conflict detection; SabreDAV warns the ETag is "often returned, but there are cases where this is not true" (e.g., when the server rewrites the object on store) — clients should re-GET when no ETag comes back. Nextcloud Tasks explicitly requires ETag integrity and breaks if a proxy/extension (e.g., CleanURLs) strips/modifies the header. CalDAV's model is "the truth is always on the server."
- **Minimal universally-accepted VTODO.** A VCALENDAR wrapper (VERSION:2.0, PRODID) containing a VTODO with UID, DTSTAMP, and SUMMARY. Add STATUS:NEEDS-ACTION and optionally DUE. This is accepted everywhere that accepts VTODO at all. Note also RFC 4791's hard rule: a calendar object resource MUST contain only one component type, so VTODO and VEVENT cannot share a .ics file.

### 6. Open-source servers worth studying

- **SabreDAV** (PHP framework) — the most influential reference; powers Baikal, Nextcloud's dav backend, ownCloud. Its "Building a CalDAV client" guide is the canonical implementer's doc, and its vobject library is the reference iCalendar parser. Study it for ETag/CTag/sync-token behavior and X- preservation. Note Nextcloud's own server had a VTODO-handling bug in time-range search (issue #45333) because SabreDAV's denormalization assumed VEVENT (DTEND vs DUE/DURATION) — instructive for VTODO edge cases.
- **Xandikos** (Python, Git-backed) — small, readable, implements WebDAV-Push, CalDAV scheduling (RFC 6638) end-to-end when all attendees are local principals, and is the test target for the `caldav` Python library. Excellent minimal reference.
- **Radicale** (Python, filesystem) — stores VTODO as opaque per-item .ics files with no server-side task logic, no recurrence expansion, no state engine (its docs describe the readers/writers as "small and stupid: they do not fully understand the iCalendar format and do not know at all what a date is"). Good for understanding the minimal viable server, and a reminder that much logic is pushed to clients. Does not support time-range calendar-query filtering.
- **Baikal** — lightweight SabreDAV packaging; faithfully stores RELATED-TO subtasks.
- **DAViCal, Cyrus IMAP/CalDAV** — mature but heavier; Cyrus is notable as a JMAP/JSCalendar pioneer alongside Fastmail.

## Recommendations

**Stage 1 — Validate the interop floor (now).** Build a thin VTODO layer on SabreDAV or Xandikos. Implement the minimal VTODO (UID/DTSTAMP/SUMMARY/STATUS) plus DUE, DTSTART, PRIORITY, PERCENT-COMPLETE, CATEGORIES, DESCRIPTION, and subtasks via RELATED-TO;RELTYPE=PARENT. Test the round-trip matrix against Apple Reminders (classic iCloud CalDAV), Tasks.org+DAVx5, Nextcloud Tasks, Thunderbird, and Evolution. **Benchmark/threshold:** if subtasks and recurrence survive round-trips on Apple Reminders + Tasks.org, CalDAV is good enough as your sync layer.

**Stage 2 — Add tasteful X- extensions.** Adopt `X-APPLE-SORT-ORDER` for manual ordering (you get Apple Reminders + Tasks.org + Nextcloud compatibility free). Use X- properties for anything proprietary (kanban column, time tracking, per-user flags), and **guarantee server-side round-trip preservation** of all unknown properties. **Threshold to change course:** if your test clients strip X- properties, move that state server-side and key it by object UID rather than embedding it in the iCalendar.

**Stage 3 — Hybrid for advanced features.** Put collaborative per-user state, dependencies, rich text, and time tracking in your own API/store keyed by VTODO UID, exposing them only in your first-party clients. Use CalDAV purely as the interop/sync surface for third-party clients. Add WebDAV-Push (Web Push + UnifiedPush) if you control the client to avoid polling.

**Stage 4 — Watch JSCalendar/JMAP.** If your roadmap is multi-year, model your internal store on JSCalendar (JSTask) the way Fastmail and Mailtemi do, so you can later expose JMAP without re-architecting. Re-evaluate when JMAP-for-tasks is standardized (JSCalendar 2.0 is in IETF draft as of Feb 2026; JMAP Calendars still excludes tasks).

**Decision rule:** if Google Workspace interop is a hard requirement, CalDAV/VTODO is disqualified (Google's CalDAV API "Doesn't support VTODO or VJOURNAL data") and you need the Google Tasks API integrated separately. If Apple + open-source ecosystem interop is the goal, CalDAV/VTODO is the right sync foundation — wrapped by a custom API for the substantial fraction of modern task-app features the protocol can't carry.

## Caveats
- **Evidence is thin on exact X-APPLE-* field semantics**: Apple does not document its iCalendar extensions; behavior is reverse-engineered from community projects (Tasks.org, elementary Tasks). Treat X-APPLE-SORT-ORDER as a community convention, not a spec.
- **Recurring-task semantics conflict between clients is well-documented but messy**; there is no authoritative resolution, and the `caldav` library itself calls the RFC's guidance underspecified ("what works on one server may break at another").
- **Client behavior changes across versions** — Thunderbird subtask support has been "coming" for 20+ years; Apple's Reminders silo migration changed the landscape in 2019. Re-test against current client versions before committing.
- **"Supports VTODO" claims are often UI-level, not sync-level** — many clients display but don't sync certain fields, or preserve-but-don't-expose. The only reliable test is an actual round-trip with byte inspection of the stored .ics.
- RFC 9253 and the moribund "Task Extensions to iCalendar" draft promise project-management features (dependencies, estimated duration) but have essentially **no client adoption** as of mid-2026; do not architect around them.
- **Apple Reminders subtask creation has interop quirks**: Nextcloud users report that subtasks created server-side can show as flat top-level reminders in Apple Reminders on macOS in some configurations, so even "supported" pairings warrant per-version verification.
